# 数据处理与结果

## 一句话结论

当前正式数据版本是 `week1_v3`：从 631 万条商品总表中筛出 8 个细分类，得到 1,992 条图文都可用的商品。数据已经完成清洗、图片校验、分层划分和 40 条人工抽查，可以用于 Week 1 基线；它还不是逐条人工确认的数据集，也不是可以直接训练文案生成模型的指令数据。

这对应 PRD“电商多模态数据集处理与标准化”部分。PRD 要求的字段统一、清洗、去重、图片可用性检查和 8:1:1 分层划分已经实现；优质文案答案和大规模人工相关性标签仍需另行建设。

## 原始数据

原始三个 JSON 位于仓库上一级，具体路径由 `configs/data.json` 管理：

- 总表：6,313,067 条。
- 原始训练 ID 表：4,418,550 条。
- 原始测试 ID 表：1,341,932 条。

总表每条商品包含 `title`、`label`、`url`、`video`、`pv`。这里的 `pv` 是商品属性字符串，不是网页浏览量。属性项用 `#;#` 分隔，属性名和值用 `#:#` 分隔。

`label` 是来源数据中的原始标签，可能表示品牌、商品类型或系列，不能直接当成标准品类。因此项目用可审阅的白名单，把它映射为一级和二级品类，并把原值保存为 `raw_label` 方便追查。

| 家居日用 | 垃圾桶 | 垃圾桶、感应垃圾桶、不锈钢垃圾桶 |

标题规则会排除配件、部分套装、工业或户外用途不符商品。v2 人工抽查发现商品 `610580284930` 是特定华硕笔记本的内置替换键盘，并非通用外接键盘；v3 因此增加“标题 + 维修件/PS/2 接口信号”的组合规则。普通 USB、蓝牙、办公或机械外接键盘不会因为标题出现“笔记本”就被删除。

规则不是训练好的分类器，也不覆盖所有商品。最终记录仍保留 `category_mapping.reviewed=false`，表示没有把 1,992 条都当作人工确认事实。

## 处理流程

1. 流式扫描大 JSON，只把目标标签写入临时 SQLite 候选库，避免一次把 631 万条数据装进内存。
2. 解析并规范化标题和 `pv` 属性；保留多值属性，不擅自猜测缺失参数。
3. 按商品 ID、标题与属性指纹、图片 URL 去重，并应用业务排除规则。
4. 使用固定种子 42 和商品 ID 哈希，每个二级品类选择 250 条。
5. 在每个二级品类内按 80%/10%/10% 划分 train、validation、test。
6. 下载图片并做完整解码、尺寸、大小和 SHA-256 校验；下载失败和相同图片不进入最终多模态数据。
7. 独立验证三个划分、字段、图片哈希和 5 条推理样本，再生成分层人工抽查表。

八类白名单共命中 29,906 条。过滤属性问题 99 条、通用标题规则 863 条、用途不符 56 条、疑似笔记本内置替换键盘 362 条、重复内容 86 条和超长 `pv` 1 条后，剩余 28,439 条候选。

## 最终规模

初选 2,000 条中，4 张图片下载或解码失败，4 条图片与已保留记录完全相同，最终为 1,992 条：

| 二级品类 | 训练 | 验证 | 测试 | 总数 |
| --- | ---: | ---: | ---: | ---: |
| 耳机 | 200 | 25 | 25 | 250 |
| 键盘 | 197 | 25 | 25 | 247 |
| 鼠标 | 199 | 25 | 25 | 249 |
| 移动电源 | 199 | 25 | 25 | 249 |
| 保温杯 | 200 | 25 | 25 | 250 |
| 收纳箱 | 199 | 25 | 25 | 249 |
| 拖把 | 198 | 25 | 25 | 248 |
| 垃圾桶 | 200 | 25 | 25 | 250 |
| 合计 | 1,592 | 200 | 200 | 1,992 |

252 条选中商品只在总表中出现，没有在来源 train/test ID 表命中，因此标为 `original_split_unknown`。当前 8:1:1 是本项目的新实验划分，不能冒充来源数据集的官方划分。

## 验证与人工抽查

- 商品 ID、内容指纹、图片 URL 指纹和最终图片 SHA-256 均唯一。
- 三个划分之间商品 ID 无交集，拆分文件与主文件一致。
- 1,992 张图片均能完整解码，文件哈希与 JSONL 记录一致。
- v3 分层抽查每类 5 条，共 40 条；品类 40/40、图片 40/40 通过。
- v2 的 40 条抽查中品类 39/40 通过，唯一失败项推动了 v3 键盘过滤规则，因此原表作为历史证据保留。

近重复检查还发现 70 个重复品牌-型号组，其中 30 组跨划分；同品类中有 13 对 dHash 接近图片，其中 6 对跨划分。它们可能是不同商家的同型号 SKU，也可能只是图片版式相似，所以本阶段没有自动删除。若 Week 2 用商品数据训练 LoRA，应先人工确认同款关系，再按型号分组划分，避免训练泄漏。

机器可读证据位于：

- `reports/data/`：当前 v3 校验、图片统计、预处理统计、抽查表和近重复审计。
- `reports/data/census/`：全量标签频数与空值统计。
- `reports/history/category_review_week1_v2.csv`：发现内置替换键盘问题的旧版人工证据。

## 运行方式

在仓库根目录执行：

~~~powershell
python -m pip install -r requirements-data.txt
python scripts/inspect_data.py --input ../product1m_product5m_id_label.json --output reports/data/census
python scripts/prepare_data.py
python scripts/download_images.py --workers 4
python scripts/prepare_inference_samples.py
python scripts/validate_data.py
python -m unittest discover -s tests -v
~~~

如果 Excel 把长商品编号保存成科学计数法，可检查或修复审核表：

~~~powershell
python scripts/repair_csv.py reports/data/category_review.csv
python scripts/repair_csv.py --repair reports/data/category_review.csv
~~~

## 已知限制

- 没有 1,992 条逐条人工品类核实，40 条抽查只用于发现系统性规则问题。
- 来源属性可能与标题或图片冲突，不能把属性直接当作已经验证的商品事实。
- 没有优质卖点、短详情等目标答案，当前数据不能直接视为 LoRA 指令集。
- 近似重复和同型号商品尚未人工裁决。
- 数据处理完成不等于正式检索指标达标；检索相关性需要单独人工标注。
