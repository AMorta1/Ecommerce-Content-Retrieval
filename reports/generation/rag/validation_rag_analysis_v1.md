## Prompt 版本演进

### rag_v1

提供身份信息、共享事实和一般事实约束。模型仍会把字段扩写成“耐用、稳定、舒适、适用场景”等效果性话术。

### rag_v2

加强禁止推断与禁止把身份信息扩写成功能的约束。扩写明显减少，但原有按品类给出的文案风格提示仍会诱导家居场景和 3C 功能扩写。

### rag_v3

使用中性、直接的字段表达，删除诱导场景或功能扩写的品类风格提示，并明确限制无事实来源的效果词。最终 24 条扩展验证使用该版本。

## 全局共享 Top-3 联合排序

候选事实先分别按标题、核心卖点和短详情三个任务的字段策略形成完整排名，再使用 Reciprocal Rank Fusion 合并：

```text
joint_score(fact) = Σ task_weight / (rrf_k + rank_task(fact))
task_weight = 1
rrf_k = 60
tasks = title, selling_points, short_description
```

最终按 `joint_score` 降序选择一个共享 Top-K。分数相同时依次使用最佳任务名次、字段顺序和 `fact_id` 确定顺序。品类、通过质量检查的品牌和型号作为身份信息单独提供，不参与 Top-K。

## Top-K 小样本比较

同一组 8 条 validation 商品在早期 Prompt 版本中比较了 Top-1、Top-3 和 Top-5：

- Top-1 经常不足以覆盖标题、卖点和短详情共同需要的信息，也更容易诱发模型自行补足内容。
- Top-5 提供更多字段，但输入事实增加后仍不能单独解决效果性扩写，且偏离首版轻量方案。
- Top-3 在事实覆盖、Prompt 长度和三个任务共同需求之间更平衡。

因此当前建议继续使用共享 Top-3。该建议来自 validation，不代表参数已经正式冻结。

RAG 共选择 65 条任务事实。逐字段初审确认 63 条被输出直接表达；遗漏的两条分别是：

- 商品 `572645689177`：`是否有麦克风=无`；
- 商品 `621341696263`：`是否机械键盘=否`。

原始字符串自动命中率为 98.6%，但布尔值“是/否/无”会与字段文字发生子串碰撞，因此以逐字段初审的 `63/65` 为准，不把自动命中率作为正式评测指标。

## Baseline 与 RAG 的主要差异

- Baseline 会接收完整属性，并频繁把材质、接口、容量等字段扩写成“耐用、稳定、快速、舒适、节省空间”等效果或使用场景。
- rag_v3 的输出主要采用“字段：值”或身份信息加字段值的直接表述，明显减少了从属性到效果的推断。
- Baseline 在商品 `621326718016` 上生成 4 条卖点，违反 1 至 3 条的解析约束；同一样本的 RAG 输出可正常解析。
- RAG 文案更短、更机械，事实约束更强，但营销表现力下降。这是当前严格 grounding 方案的直接结果。

## rag_v3 Bad Case

事实扩写初审发现 2/24 条仍有不受任务事实支持的场景话术：

- `585183140226`：短详情新增“适用于家居日用”；
- `613971147597`：卖点和短详情新增“适用于家居收纳”。

另有输出完整性问题：

- 两条已选任务事实未被表达；
- 当可用任务事实少于 3 条时，模型会用品牌、型号或品类补足卖点。内容来自已提供身份信息，不构成新事实，但不符合“卖点逐条对应任务事实”的理想格式。

逐样本记录见 `validation_rag_review_v3.csv`。

## 当前结论

RAG 链路、全局共享 Top-3、Prompt 注入、模型 revision 记录、输出解析和实验日志已经跑通。`rag_v3` 相比早期 Prompt 和配对 Baseline 显著收紧事实边界。

当前配置尚不建议立即锁定并运行正式 test100。进入 frozen test 前，仍需在 validation 上解决两项明确问题：

1. 禁止把品类身份改写成“适用于某场景”；
2. 检查所有已选任务事实是否被表达，并避免用身份信息替代已选事实。

此外，当前输出接口要求恰好 3 条卖点，而部分商品只有 1 至 2 条合格任务事实。是否允许卖点减少为 1 至 3 条会改变现有输出解析契约，不能在本阶段自行决定；若保持 3 条，则需接受直接重复或使用身份信息作为事实性信息点。该事项需要在锁定配置前确认。

已确认的事实约束修正不需要改变模型、解码参数、数据划分、Top-3 联合排序或评测口径。
